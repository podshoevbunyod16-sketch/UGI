# UGI — Unified General Intelligence

## UDI Research MVP — проверяемый поиск контроллера

Репозиторий UGI (Unified General Intelligence), содержащий минимальный вертикальный прототип Unified Discovery Intelligence. Проект демонстрирует полный цикл:

```text
problem contract
→ 3 альтернативных представления
→ реальные мутации
→ проверка инвариантов
→ межмодельный перенос мутаций
→ численная оптимизация
→ held-out evaluation
→ environment-suite evaluation
→ zero-shot parameter transfer
→ preregistered random suite
→ adversarial/boundary stress suite
→ automatic resilience report
→ конкурирующие гипотезы
→ выбор вычислительного эксперимента
→ воспроизводимая симуляция
→ verification report
```

## Научная задача

Управление простой дискретной системой:

```text
x[t+1] = a * x[t] + b * u[t] + disturbance[t]
```

Цель — удерживать `x` около нуля при ограничении управляющего воздействия. MVP сравнивает три структуры:

- `proportional`: прямое обратное управление `u = -k*x`;
- `damped`: обратная связь с демпфированием изменения состояния;
- `bounded`: прямое управление с ограничением актуатора.

Это не утверждение о новом контроллере. Это воспроизводимый стенд для проверки самого UDI-процесса.

## Phase 1/2: межмодельный перенос

MVP также создаёт две разные формулировки одной задачи:

- `CausalGraph`: DAG с узлами `disturbance`, `state`, `control`, `next_state`, `objective`;
- `OptimizationFormulation`: переменные, objective и ограничения динамики/актуатора.

Оператор `causal_edge_to_optimization_constraint` переносит мутацию `disturbance → control` из причинного графа в оптимизационную модель как ограничение политики, зависящей от `disturbance_t`. Перенос сохраняется с provenance и проверяется по инвариантам. Попытка добавить `next_state → state` отклоняется из-за причинного цикла и не продвигается в подтверждённую популяцию.

## Phase 3: численный оптимизатор

Добавлен детерминированный coordinate-descent оптимизатор для политики:

```text
u[t] = clip(-k * state[t] + q * disturbance[t])
```

Baseline оптимизирует только `k` (`q=0`). Перенесённая модель оптимизирует `k` и `q`, но разрешается только при фактически принятом переносе `disturbance → control`. Сравнение использует одинаковые seed, сценарий, horizon и ограничения актуатора и сохраняет абсолютное и относительное улучшение целевой функции.

## Phase 4: held-out evaluation

Параметры оптимизируются только на `alternating` (train scenario). Затем замораживаются и без повторной оптимизации проверяются на независимых сценариях:

- `nominal` — малый случайный шум;
- `pulse` — одиночный импульс;
- `ramp` — медленно меняющееся возмущение.

Для каждого held-out сценария baseline и transferred policy получают одинаковую последовательность возмущений, seed и ограничения актуатора. Отчёт сохраняет objective обеих моделей, абсолютное/относительное улучшение, стабильность, число побед перенесённой модели и факт отсутствия re-optimization. Если улучшение исчезает на held-out данных, это фиксируется как evidence против обобщения, а не скрывается.

## Phase 5: новые динамические системы

Добавлен environment suite с изменёнными параметрами `a`, `b` и `control_limit`. Для каждой системы заново создаются причинный граф и оптимизационная формулировка, применяется тот же оператор `disturbance → control`, а параметры `k` и `q` калибруются отдельно в рамках одинакового бюджета. Отчёт проверяет, что структурный перенос принят во всех средах, сравнивает objective baseline/transferred и сохраняет стабильность каждой системы.

## Phase 6: zero-shot перенос параметров

Добавлен строгий режим без перекалибровки: параметры `k` и `q`, найденные в source environment, замораживаются и применяются к новым системам. В target environments optimizer не вызывается. Отдельно проверяются структурный перенос, objective baseline/transferred, stability и actuator bounds. Это позволяет отличить устойчивость самой мутации от эффекта локальной подгонки параметров.

## Phase 7: preregistered random zero-shot suite

Перед генерацией фиксируются критерий успеха и диапазоны параметров. По отдельному seed создаются 20 детерминированных новых систем:

- `state_a ∈ [0.88, 1.20]`;
- `input_b ∈ [0.35, 1.10]`;
- `control_limit ∈ [0.60, 1.20]`;
- `disturbance_scale ∈ [0.70, 1.30]`.

Заранее зарегистрированный критерий: минимум 20 target-систем, win rate transferred policy не ниже 75%, stable rate не ниже 95%, среднее относительное улучшение не ниже 0%. После генерации критерий не изменяется, source-параметры заморожены, а optimizer в target-системах не запускается.

## Phase 8: adversarial и boundary cases

Добавлен отдельный stress protocol с фиксированными сложными средами: высоким `state_a`, слабым `input_b`, малым `control_limit`, сильным возмущением и низкой authority управления. Критерий этого протокола противоположен обычному benchmark: он считается пройденным, если suite содержит обе категории и обнаруживает хотя бы один явный failure mode — ухудшение transferred objective, instability или actuator saturation. Это проверяет способность системы честно обнаруживать границы применимости, а не маскировать срыв zero-shot переноса.

## Phase 9: автоматический отчёт и рекомендации

После каждого CLI-запуска автоматически создаются `artifacts/phase9_report.json` и `artifacts/phase9_report.md`. Генератор работает детерминированно и использует только фактически записанные результаты Phase 4–8. Он агрегирует failure modes, связывает каждую рекомендацию с evidence и формирует конкретный следующий verification experiment. Приоритеты назначаются прозрачными правилами: instability → `critical`, saturation/ухудшение → `high`, положительная, но ограниченная обобщаемость → `medium`.

## Запуск

Из каталога проекта:

```bash
python3 -m unittest discover -s tests -v
python3 -m udi_mvp --seed 20261108 --output artifacts/report.json
```

Markdown-отчёт создаётся рядом с JSON:

```text
artifacts/report.md
```

Тесты используют только стандартную библиотеку Python 3.12+.

## Структура

- `udi_mvp/core.py` — формальные контракты, причинный граф, оптимизационная формулировка, межмодельный перенос, численный оптимизатор, мутации, инварианты, симуляция и scoring.
- `udi_mvp/__main__.py` — CLI и генерация отчёта.
- `udi_mvp/reporting.py` — автоматический Phase 9 отчёт и синтез рекомендаций.
- `tests/test_core.py` — unit, negative, invariant и reproducibility tests.
- `artifacts/` — фактически созданные результаты запуска.

## Честные ограничения MVP

- Нет физического эксперимента: только bounded computational simulation.
- Нет внешних данных и LLM-зависимости.
- Система не доказывает патентную или научную новизну.
- Score предназначен для сравнения внутри фиксированного benchmark и не является универсальной метрикой качества.
- Робастность проверяется на заранее заданных сценариях, а не на всех возможных динамических системах.
